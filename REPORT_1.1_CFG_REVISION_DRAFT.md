# §1.1 CFG revision record

The revised report treats a client as a CFG over the existing `Op`
alphabet instead of treating a flat `Seq<Op>` as the client model. Keep
`Op` as
the operation alphabet, but describe a family of client interactions by
a CFG over those operations. Nonterminals capture reusable client
structure such as loops, guarded regions, and nested API workflows. The
CFG denotes client behaviors; it is not assumed to be regular, and it
is not assumed to equal the set of all traces permitted by `op_pre`.

The top-down check is: derive candidate top-level properties from the
client patterns and their intended outcomes, then verify that executions
generated by the CFG satisfy those properties under the existing API
contracts. If a property is not derivable, produce a counterexample and
distinguish a client/property modeling error from a missing or weak API
contract. A successful result is scenario evidence for the client
patterns and assumptions represented by that CFG, not a completeness
claim for every client.

Replace the existing “Seq<Op> is the client encoding” idea with the
following:

> **The real kernel client is available, and a CFG is the intended
> representation of its interaction patterns.** `Op` already lifts the
> public mm API into an event alphabet. A concrete path can be recorded
> as a witness word, while a CFG generalizes recurring client structure
> into a family of paths. The client grammar supplies the top-down
> scenarios; `op_pre` and `lemma_step` supply the existing API-side
> constraints. The goal is to infer and prove client-relevant top-level
> properties, then use counterexamples to locate API-spec gaps. An LLM
> may help translate upstream call patterns into candidate productions,
> with review and proof providing the evidence.

Replace the application step that asks to encode two or three paths as
`Seq<Op>` with:

> **Represent two or three real Asterinas call paths as CFG productions**
> over the `Op` alphabet, recording which productions are directly
> grounded in source and which are hypotheses. For example, express the
> client workflow around `OpenCursorMut`, `FrameFromUnused`, `Map`,
> `DropCursor`, and `Query`; state the expected property that `Query`
> observes the page installed by `Map`; then prove that every generated
> path satisfies it under the current `run` contracts. Preserve concrete
> witness paths and counterexamples. Do not require equality between
> the client language and the API-permitted language: the client is a
> particular usage family, so the relevant relation is that its traces
> are supported by the API contract and establish the client property.

## Pilot results

The spec-backed Mutex pilot in `mutex_client_cfg.v` abstracts the real
Asterinas character-device registry `lookup` helper with the CFG
`Client -> ε | Acquire Lookup Release Client`, `Lookup -> Access`. Rocq
proves the lock discipline and that its projected traces are generated
by the existing formal mutex protocol CFG. `Access` is erased by that
protocol abstraction, so the pilot does not prove map lookup correctness
or find a spec gap.

The companion SpinLock pilot in `CLIENT_CFG_CASE.md` grounds this representation
in `xarray_client_cfg.v`: the XArray insertion loop has CFG
`Client -> ε | Acquire Body Release Client`,
`Body -> ε | Store Body`. Rocq proves that each body runs while locked,
each complete client trace returns unlocked, and erasing the client-only
`Store` events yields a trace accepted by the existing SpinLock model.
The pilot is partial: it manually derives one sequential usage pattern,
and the current SpinLock model is implementation-derived because this
repository has no independent formal SpinLock spec. Therefore it does
not yet demonstrate an authoritative spec-gap finding.

The COW pilot in `mm_cow_client_cfg.v` now makes the missing cross-tool
abstraction explicit. `PageViewObservation` records the selected mapping's
physical address, writable bit, and RAM/IoMem kind; `state_refines_observation`
relates a pair of these observations to the Rocq candidate state. The
`ApiObservationPost` relation lists the one-page postconditions required for
each state-changing event, and Rocq proves that traces satisfying those
postconditions simulate the candidate CFG state transitions. The postconditions
are currently Rocq premises: connecting them to actual Vostd `CursorView` and
runtime operation contracts remains open. This is a precise proof obligation,
not yet evidence that the COW client property follows from Vostd contracts.
For the selected witness, Rocq constructs an `ApiObservationTrace` and proves
that erasing its final observation equals the candidate `run` result. The
remaining proof must establish those observation postconditions from the
runtime Vostd APIs.
